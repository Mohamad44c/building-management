This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `pnpm dev` — start dev server (http://localhost:3000)
- `pnpm devsafe` — dev server with `.next` cache wiped first (use if hitting stale build issues)
- `pnpm build` — production build
- `pnpm lint` — Next/ESLint check
- `pnpm generate:types` — regenerate `src/payload-types.ts` from `src/payload.config.ts` (run after changing any collection schema)
- `pnpm generate:importmap` — regenerate `src/app/(payload)/admin/importMap.js` (run after adding/changing custom admin components referenced via `admin.components`)
- `pnpm test:int` — Vitest integration tests (`vitest run --config ./vitest.config.mts`, tests in `tests/int/**/*.int.spec.ts`, jsdom env)
- `pnpm test:e2e` — Playwright e2e tests (`tests/e2e`, auto-starts dev server via `webServer`)
- `pnpm test` — runs both int then e2e
- Single test file: `pnpm exec vitest run tests/int/api.int.spec.ts --config ./vitest.config.mts` or `pnpm exec playwright test tests/e2e/frontend.e2e.spec.ts`

## Architecture

This is a **Payload CMS 3.x** app (admin backend) built on **Next.js 15 App Router**, with a custom **React frontend dashboard** at `/` that reads data collected through the Payload admin.

### Two route groups, one app

- `src/app/(payload)/` — Payload's admin UI and REST/GraphQL API routes (`/admin`, `/api/*`). Mostly generated/managed by Payload; `importMap.js` is regenerated by `pnpm generate:importmap` and should not be hand-edited except to add entries matching `admin.components` paths in `payload.config.ts`.
- `src/app/(frontend)/` — the actual building-management dashboard UI shown at `/`. `middleware.ts` gates the root path `/`: if no `payload-token` cookie is present, it redirects to `/admin/login?redirect=/`. So the dashboard is only reachable by authenticated Payload users.

### Data flow: Payload collections → pure metrics → two server actions → React Query → dashboard components

1. **Collections** (`src/collections/*.ts`) define the schema: `Buildings`, `Tenants`, `Payments`, `Invoices`, `Expenses`, `ExpenseCategories`, `DieselExpenses`, `GeneratorExpenses`, `GeneratorHours`, `Users`. Relationships: `Tenants.building → Buildings`, `Payments.tenant → Tenants`, `Expenses.category → ExpenseCategories`.
2. **Pure metrics** — all dashboard math lives in side-effect-free functions (docs in, numbers out), tested in `tests/int/dashboardMetrics.int.spec.ts`: `src/lib/dashboardMetrics.ts` (rent, receivables aging, forecasts, tenants/payments/expenses), `src/lib/generatorStats.ts` (current vs comparison-window generator stats, daily hours), `src/lib/dashboardDateFilter.ts` (period presets → windows).
3. **Timezone** — every day/month boundary is in the business timezone `BUSINESS_TIME_ZONE` (`Asia/Beirut`) via `src/lib/businessTime.ts`, never server-local or browser-local time. Invoices are matched to a period by `periodYear`/`periodMonth` month keys, not instants.
4. **Server actions** — `src/server/dashboard.ts` exposes exactly two actions: `getDashboardPeriodData(filter)` (follows the period filter) and `getDashboardOverview()` (live snapshot + forecasts). Each runs its Payload queries in parallel with `select`/`depth: 0`. Keep it at two: Next.js runs a client's server actions sequentially, so many small actions become a waterfall. Actions rethrow on failure so the UI shows an error rather than `$0.00`. Every export of a `'use server'` file is a public endpoint — validate inputs (`parseDashboardFilter`) and call `requireUser()`.
5. **Prefetch + hooks** — `src/app/(frontend)/page.tsx` prefetches both queries on the server and hydrates them (`HydrationBoundary`); `src/hooks/use-dashboard.ts` wraps the actions with keys from `src/lib/dashboardQueryKeys.ts` (shared by server and client, keyed by filter + business day). Period changes keep the previous data on screen (dimmed) while loading.
6. **UI** — `src/app/(frontend)/components/home-dashboard.tsx` calls the two hooks and passes slices to presentational components in `src/components/charts/*` built on `src/components/dashboard/*` (`Panel`, `StatCard`, `Delta`, `BarList`). Charts use `recharts` via `src/components/ui/chart.tsx`. The sticky `dashboard-header.tsx` holds the period filter (`src/components/ui/dashboard-period-filter.tsx`: presets + last 12 months). Theme is `next-themes` (class strategy) in `src/components/providers.tsx`.
7. Admin users can jump from the Payload admin panel to the dashboard via `OpenDashboardButton` (`src/components/admin/OpenDashboardButton.tsx`), wired into `payload.config.ts` under `admin.components.actions`.

### Diesel expense payment logic

Diesel invoices track partial payments (`amountPaid`) alongside a boolean `isPaid`. The invariants are centralized rather than duplicated:

- `src/lib/dieselExpenseBalance.ts` — pure helpers (`effectiveAmountPaid`, `remainingBalance`, `resolvePaidState`, `roundCents`) used by the DieselExpenses and Invoices hooks and dashboard aggregation (`src/lib/dashboardMetrics.ts`). `isPaid === true` always means fully paid (legacy rows have `amountPaid` backfilled to 0). `resolvePaidState` infers intent from what changed vs the original doc, because the admin form resubmits every field.
- `src/collections/dieselExpenseHooks.ts` — a `beforeChange` hook (`syncDieselPaymentFields`) on `DieselExpenses` that recomputes `totalAmount`, clamps `amountPaid` to `[0, total]`, and keeps `isPaid` in sync (including "mark paid" via checkbox without an explicit `amountPaid`, and reopening a settled invoice).
- `summarizeDieselOutstanding` in `src/lib/dashboardMetrics.ts` sums remaining balances across unpaid/partially-paid invoices for the outstanding-balance dashboard card — deliberately independent of the dashboard's date-range filter.

When touching diesel payment fields, keep these three in sync; the balance math should only ever live in `dieselExpenseBalance.ts`.

### Generator stats

`src/lib/generatorStats.ts` computes current-vs-comparison generator stats (diesel invoiced/liters, runtime, maintenance, cost per run-hour and per running day, daily hours timeline) from docs covering both windows. Comparison windows come from `resolveDashboardDateWindow`: partial periods compare the same days-to-date (Sep 1–29 vs Aug 1–29), full months compare the previous full span. The next-oil-change estimate treats the oil-change expense's `hours` as the **meter reading at service** and assumes a 250 h interval (`SERVICE_INTERVAL_HOURS`).

### UI conventions

- Components use shadcn/ui conventions (`components.json`: style `new-york`, base color `neutral`, RSC on). Path aliases: `@/components`, `@/lib`, `@/hooks`, `@/ui` all resolve under `src/` (see `tsconfig.json` paths and `components.json` aliases).
- Styling is Tailwind v4 (`@tailwindcss/postcss`), with dark mode via `next-themes` (`src/components/theme-toggle.tsx`, `src/hooks/use-theme.ts`).
- Charts share a common wrapper/theme in `src/components/ui/chart.tsx`; new charts should use it rather than raw `recharts` for consistent theming/legends/tooltips.

### Database

Postgres via `@payloadcms/db-postgres`, configured from `DATABASE_URI` env var. The `.env` `DATABASE_URI` points at the **production** database.

Schema push is disabled (`push: false`), so changing a collection schema does not touch the DB. Workflow: `pnpm payload migrate:create <name>` → review the generated file in `src/migrations/` → test it against a restored copy of prod (`pg_dump -Fc` + `pg_restore` into a local Postgres) → take a fresh backup → `pnpm payload migrate`. Never rename or remove fields in a migration without a data-preserving step. `docker-compose.yml`/`Dockerfile` are available for local Postgres if not running it natively.
