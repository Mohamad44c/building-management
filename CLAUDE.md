# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `pnpm dev` — start dev server (http://localhost:3000)
- `pnpm devsafe` — dev server with `.next` cache wiped first (use if hitting stale build issues)
- `pnpm build` — production build
- `pnpm lint` — Next/ESLint check
- `pnpm generate:types` — regenerate `src/payload-types.ts` from `src/payload.config.ts` (run after changing any collection schema)
- `pnpm generate:importmap` — regenerate `src/app/(payload)/admin/importMap.js` (run after adding/changing custom admin components referenced via `admin.components`)
- `pnpm test:int` — Vitest integration tests (`vitest run --config ./vitest.config.mts`, tests in `tests/int/**/*.int.spec.ts`, jsdom env)
- `pnpm test:e2e` — Playwright e2e tests (`tests/e2e`, auto-starts dev server via `webServer`)
- `pnpm test` — runs both int then e2e
- Single test file: `pnpm exec vitest run tests/int/api.int.spec.ts --config ./vitest.config.mts` or `pnpm exec playwright test tests/e2e/frontend.e2e.spec.ts`

## Architecture

This is a **Payload CMS 3.x** app (admin backend) built on **Next.js 15 App Router**, with a custom **React frontend dashboard** at `/` that reads data collected through the Payload admin.

### Two route groups, one app

- `src/app/(payload)/` — Payload's admin UI and REST/GraphQL API routes (`/admin`, `/api/*`). Mostly generated/managed by Payload; `importMap.js` is regenerated by `pnpm generate:importmap` and should not be hand-edited except to add entries matching `admin.components` paths in `payload.config.ts`.
- `src/app/(frontend)/` — the actual building-management dashboard UI shown at `/`. `middleware.ts` gates the root path `/`: if no `payload-token` cookie is present, it redirects to `/admin/login?redirect=/`. So the dashboard is only reachable by authenticated Payload users.

### Data flow: Payload collections → server actions → React Query hooks → chart components

1. **Collections** (`src/collections/*.ts`) define the schema: `Buildings`, `Tenants`, `Payments`, `Expenses`, `ExpenseCategories`, `DieselExpenses`, `GeneratorExpenses`, `GeneratorHours`, `Users`. Relationships: `Tenants.building → Buildings`, `Payments.tenant → Tenants`, `Expenses.category → ExpenseCategories`.
2. **Server actions** in `src/server/expenses.ts` (`'use server'`) call `getPayload({ config: configPromise })` and run `payload.find(...)` queries, then shape/aggregate the data (grouping by building, by category, by day, etc.) for the dashboard.
3. **Hooks** in `src/hooks/*.ts` wrap those server actions in `@tanstack/react-query` `useQuery` calls (e.g. `use-expenses.ts`, `use-generator-hours.ts`, `use-payments.ts`, `use-tenants.ts`).
4. **Chart components** in `src/components/charts/*.tsx` consume the hooks and render with `recharts` via the shared `src/components/ui/chart.tsx` wrapper.
5. The dashboard page composes everything: `src/app/(frontend)/components/home-dashboard.tsx` lays out `DashboardHero` (period filter, theme toggle) and grouped `DashboardSection`s of charts. Date filtering is driven by a shared `DashboardPeriodValue`/`DateRange` (`preset: 'today' | 'week' | 'month' | 'year' | 'custom'`) passed down from `home-dashboard.tsx` state into hooks/server actions — most server actions in `expenses.ts` take a `(range, monthIndex?)` pair and compute `startDate`/`endDate` accordingly.
6. Admin users can jump from the Payload admin panel to the dashboard via `OpenDashboardButton` (`src/components/admin/OpenDashboardButton.tsx`), wired into `payload.config.ts` under `admin.components.actions`.

### Diesel expense payment logic

Diesel invoices track partial payments (`amountPaid`) alongside a boolean `isPaid`. The invariants are centralized rather than duplicated:

- `src/lib/dieselExpenseBalance.ts` — pure helpers (`effectiveAmountPaid`, `remainingBalance`, `roundCents`) used by both the collection hook and dashboard aggregation. Legacy rows without `amountPaid` infer fully-paid from `isPaid === true`.
- `src/collections/dieselExpenseHooks.ts` — a `beforeChange` hook (`syncDieselPaymentFields`) on `DieselExpenses` that recomputes `totalAmount`, clamps `amountPaid` to `[0, total]`, and keeps `isPaid` in sync (including "mark paid" via checkbox without an explicit `amountPaid`, and reopening a settled invoice).
- `getDieselOutstandingSummary` in `src/server/expenses.ts` sums remaining balances across unpaid/partially-paid invoices for the outstanding-balance dashboard card — deliberately independent of the dashboard's date-range filter.

When touching diesel payment fields, keep these three in sync; the balance math should only ever live in `dieselExpenseBalance.ts`.

### Generator stats

`src/lib/generatorStats.ts` computes period-over-period generator statistics (diesel spend/liters, generator hours, maintenance cost, cost per day/hour, daily timeline) given a `Payload` instance and a `DashboardPeriod`. It's called from the `getGeneratorDashboardStats` server action and is where current-vs-previous period comparison windows are computed.

### UI conventions

- Components use shadcn/ui conventions (`components.json`: style `new-york`, base color `neutral`, RSC on). Path aliases: `@/components`, `@/lib`, `@/hooks`, `@/ui` all resolve under `src/` (see `tsconfig.json` paths and `components.json` aliases).
- Styling is Tailwind v4 (`@tailwindcss/postcss`), with dark mode via `next-themes` (`src/components/theme-toggle.tsx`, `src/hooks/use-theme.ts`).
- Charts share a common wrapper/theme in `src/components/ui/chart.tsx`; new charts should use it rather than raw `recharts` for consistent theming/legends/tooltips.

### Database

Postgres via `@payloadcms/db-postgres`, configured from `DATABASE_URI` env var. `docker-compose.yml`/`Dockerfile` are available for local Postgres if not running it natively.
